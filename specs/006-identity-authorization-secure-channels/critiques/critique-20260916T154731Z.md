# Spec 006 Independent Critique

**Feature:** Identity, Authorization, and Secure Channels  
**Review date:** 2026-09-16  
**Inputs:** `spec.md`, `plan.md`, `research.md`, `data-model.md`, all four `contracts/*.md`, `quickstart.md`, roadmap brief `roadmap-reviews/brief-20260916T153825Z.md`, and `.specify/memory/constitution.md`  
**Review mode:** Independent Product and Engineering lenses, proposed edits only. No primary artifacts were changed.

## Executive Summary

**Verdict: PROCEED WITH UPDATES, do not generate implementation tasks until the Must-Address item is resolved.**

The feature has strong user value and unusually good protocol specificity: it establishes a local trust root, paired extension identity, authenticated encrypted channels, least-privilege authorization, object-existence privacy, and serialized rotation/revocation. The roadmap brief confirms scope and dependency alignment, and the plan preserves the Spec 001 profile and the constitution's boundaries.

One security-contract contradiction is blocking. `FR-003` permits a private key to be transferred in an authenticated native channel for an enrollment bundle, while the bootstrap/enrollment contract, research decision, `FR-004`, quickstart, and constitution's least-privilege posture require that private keys never cross bootstrap transport or enter application state. This cannot be left to implementation interpretation: it changes the trust boundary and can make a valid implementation violate the stated invariant.

Additional recommendations concern enrollment-rate-limit semantics, recovery UX, measurable performance/evidence definitions, event-volume operations, and the dependency contracts owned by Specifications 007 and 009. These do not invalidate the architecture, but should be addressed before implementation tasks are frozen.

## Product Lens Findings

### P1 -- Must-Address: pairing contract contradicts the private-key non-disclosure user promise

**Evidence:** `spec.md` `FR-003` says a private key *may* be transferred inside an authenticated encrypted native channel for inclusion in an enrollment bundle. `FR-004` says native setup must not send private keys over an unauthenticated route, the enrollment/bootstrap contract and `research.md` explicitly say no private key crosses the route. `quickstart.md` expects zero private bytes in bootstrap captures, and the constitution requires no browser credential export and least privilege.

**Why it matters to users:** A user cannot know whether setup leaves the intended platform/extension key store or whether a captured setup transcript contains a reusable secret. An authenticated channel protects in transit but does not make a private-key export acceptable at this trust boundary.

**Proposed exact edit (do not apply in this review):** In `spec.md` `FR-003`, replace the private-key-transfer exception with: “Private keys MUST be generated and retained by the owning platform credential store or extension-local storage, only the public key, fingerprint, and non-secret enrollment metadata may cross bootstrap/enrollment channels. Private key bytes MUST NOT be transferred, serialized, QR-encoded, logged, or placed in durable application state.” Align `FR-004`, the entity definition for `Credential Reference`, and any affected acceptance wording with this rule. If private-key transfer is  required, remove the absolute no-disclosure claims and add a separate threat-model decision and explicit user-visible export ceremony, do not retain the current ambiguous exception.

### P2 -- Recommendation: define the user's recovery action for each failed setup/pairing state

**Evidence:** Contracts require `boundary`, stable `code`, and `safe_next_action`, but `safe_next_action` remains a general field rather than a defined action map. Quickstart enumerates credential mismatch, expired/consumed/revoked bundles, wrong origin/install metadata, and rate limiting without specifying which CLI/setup action safely recovers each case.

**Why it matters to users:** Setup failures are the primary user-facing journey. “Retry” is unsafe or ineffective for consumed, revoked, mismatched, or rate-limited states, users need deterministic instructions that do not leak whether a protected object exists.

**Proposed exact edit:** Add a small normative table to `contracts/failures-events.md` mapping each externally reachable code to one safe action (for example: `credential_store.unavailable` → install/enable the platform store and rerun `doctor`, `credential_store.mismatch` → stop and inspect the selected state directory, `origin.rejected` → reinstall/enable the exact paired extension, `rate_limited` → wait until the returned bounded retry window and do not resend proofs, `revoked`/`stale_epoch` → reconnect or repeat administrator pairing). State that actions are bounded, contain no protected fields, and must not distinguish unknown from unauthorized objects.

### P3 -- Question: is address-based enrollment limiting intentionally per-host, or should it be per bundle/principal?

**Evidence:** `FR-009` and the quickstart require ten failed attempts per loopback address per minute, while all supported peers share `127.0.0.1`/`::1`. The bundle also closes after five failed proofs. No reset, scope, or interaction between the two counters is defined.

**User/product risk:** One broken or malicious local client can deny pairing for every legitimate client on the machine. Conversely, a limit scoped too narrowly may permit brute-force attempts across bundles.

**Proposed exact edit:** Add a clarification in `spec.md` and `contracts/enrollment-bootstrap.md` defining the rate-limit key (for example, `(state-directory, enrollment authority, loopback address)`), window start/reset, whether rejected malformed envelopes count, how the five-proof bundle counter combines with the address counter, and the bounded retry information returned. Add one acceptance scenario for exhaustion by one client followed by a legitimate client, and one for expiry/reset.

## Engineering Lens Findings

### E1 -- Must-Address: resolve conflicting trust-boundary invariants before implementation

This is the engineering manifestation of P1 and is a contract-level blocker, not a wording issue. The plan's sequencing step 3 says to implement inherited-pipe bootstrap and enrollment carriers, while step 6 enrolls. Different engineers can follow `FR-003` and still produce a design that fails `SC-001`, the enrollment contract, or the research decision. The contradiction also affects deterministic vectors and the claim that no private bytes occur in captured bootstrap bytes.

**Proposed exact edit:** Apply the P1 edit and add a single cross-artifact invariant to `research.md`, `contracts/enrollment-bootstrap.md`, and `plan.md` sequencing step 3: “Enrollment carries a public key and non-secret proof metadata only, key generation/signing stays behind the owning credential-store interface.” Add a vector/assertion that the encoded native bootstrap and enrollment envelopes contain no private-key field and reject one if supplied.

### E2 -- Recommendation: pin the 007/009 integration contracts before task decomposition

**Evidence:** `research.md` and `plan.md` defer durable transition/recovery carriers to Spec 007 and expiry/clock semantics to Spec 009. Yet requirements for crash-before/after-commit, uncertain outcomes, ten-minute expiry, stale epochs, and serialized races depend on those interfaces. The roadmap brief only verifies Spec 005 and does not provide these downstream contracts.

**Risk:** Tasks can independently invent persistence and deadline semantics, producing incompatible recovery behavior or a security check outside the owning state actor.

**Proposed exact edit:** Add a “required upstream/downstream contract inputs” section to `plan.md` before Implementation Sequencing specifying the minimum 007 interface (transaction outcome identity, commit/recovery status, serialization boundary, uncertain-outcome carrier) and 009 interface (monotonic deadline/expiry result, wall-clock uncertainty behavior, test clock injection). Mark task generation blocked until these contracts are either published or explicitly accepted as versioned temporary interfaces. Add a plan acceptance criterion that all race and crash scenarios use those same interfaces.

### E3 -- Recommendation: perform and malformed-input criteria reproducible

**Evidence:** The plan states warm-channel median ≤100 ms and p95 ≤250 ms “for the measured local scenario,” while `SC-007` requires 100,000 bounded malformed/oversized cases. Neither identifies hardware, message size, warm-up, concurrency, implementation mode, measurement tool, distribution, or pass/fail rule.

**Risk:** A performance claim can pass under an artificially favorable fixture, and a malformed-input campaign can be nominally run without proving allocation bounds or exercising all parser boundaries.

**Proposed exact edit:** In `plan.md` and `quickstart.md`, define the benchmark scenario (OS/CPU class, Rust release mode, channel already established, payload size, concurrency, sample count, warm-up, median/p95 calculation) and the regression threshold. Define the malformed corpus categories and required counters: pre-allocation rejection, maximum observed allocation, channel closure, dispatch count (must remain zero), and secret/event-leak scan. Keep the product claim scoped to that named scenario per constitution V.

### E4 -- Recommendation: specify event-volume and retention controls without weakening audit integrity

**Evidence:** Security emits events for authentication failures, malformed input, replay, downgrade, rate limits, and authorization denial, the daemon persists append-only digest-chained events. There is no bound on event size, rate, queue/storage growth, retention, or behavior when the event sink is unavailable.

**Risk:** A local peer can generate high-volume failures and exhaust daemon storage or block the state actor. Dropping events could also compromise the intended audit invariant.

**Proposed exact edit:** Add to `contracts/failures-events.md` and the plan: bounded event field lengths, per-boundary aggregation/rate limiting, a daemon-owned storage quota/retention policy, and an explicit fail-closed/fail-safe rule for sink exhaustion (security transitions must not disclose protected data or proceed without required audit facts, while health remains bounded). Include a quickstart scenario proving event flooding cannot exceed configured limits and that digest-chain continuity is preserved.

### E5 -- Question: what is the supported extension-key recovery/re-pairing behavior?

**Evidence:** The plan places the extension private key in `chrome.storage.local` and the spec requires rotation/revocation, but no contract covers extension storage clearing, profile migration, extension reinstall, backup/restore, or key replacement after loss. `FR-024`/`FR-025` define administrator rotation/revocation but not the user-visible recovery path for a missing local key.

**Risk:** A legitimate user may be locked out or prompted into unsafe re-enrollment, an implementation may accidentally accept a new key without explicit revocation of the old principal.

**Proposed exact edit:** Add a clarification and acceptance scenario: missing/unusable extension key yields a bounded `credential_store.mismatch`/`revoked` outcome, never silently regenerates access, administrator-mediated re-pairing creates a new principal or explicitly rotates the old one, advances epoch, closes old channels, and records an idempotent transition. State whether extension-local backup is unsupported (recommended for first release).

## Cross-Lens Synthesis

1. **Highest overlap:** The private-key transfer exception is simultaneously a product trust promise, a protocol invariant, and a constitution/least-privilege concern. Resolve it once, consistently across all artifacts, before task generation.
2. **Value-preserving simplification:** Public-key-only enrollment is simpler than supporting secret transfer, removes an export path, and makes the existing quickstart assertion testable.
3. **Boundary clarity:** 007 owns durable transition/recovery and 009 owns time, Spec 006 should publish the minimum typed contracts it consumes rather than leaving their semantics implicit.
4. **Operational completeness:** Stable failures are valuable only when their safe next actions and bounded event behavior are concrete enough for setup tooling and incident diagnosis.
