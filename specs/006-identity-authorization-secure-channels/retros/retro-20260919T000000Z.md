## Specification and plan accuracy

The implementation covered the stated FR/SC inventory and stayed within the intended product scope. The analysis found 100% task trace coverage for the 41 buildable identifiers, with three governance tasks intentionally blocked. However, the plan was not fully authoritative during implementation: it described a ring-only cryptographic dependency boundary while the implementation temporarily used `p256`, and it described an unchanged runtime while runtime enrollment integration was added. The accepted review and implementation became the practical authority, but the divergence should have been recorded earlier in a decision artifact.

The task ledger also contained identifier drift: ADR tasks refer to `adr-5` and `adr-6` while repository MADR files are 0006 and 0007; review shorthand uses T007 for expiry and T019H for a nonexistent task. These did not invalidate the delivered behavior, but they made traceability harder. The three unchecked ADR tasks remain unchecked because their text forbids claiming completion when Beads is unavailable.

Plan score: **ADEQUATE**. The architecture and decomposition supported delivery, but the dependency/runtime divergence, identifier drift, and governance prerequisite mismatch reduced its value as a single source of truth.

## What went well

- The six-pass review process converged instead of accepting the first green report. It found semantic errors in deadlines, required rejection facts, host-budget ordering, event-unavailable mutation, endpoint classification, and dependency boundaries.
- The final review established a 16-exit table proving fact-before-mutation on reachable exits. This turned an informal security property into explicit evidence.
- Mutation proof was the decisive quality practice. Reintroducing a defect and requiring a named test to fail with a specific message exposed tests that merely exercised code without defending behavior.
- The final suite was broad and reproducible: 427 default tests, 435 all-features tests, and 230 listed security-library tests, plus focused lifecycle and advisory checks.
- Scope boundaries were ultimately respected. Browser realization and durable history remained downstream-owned, and no production source change was required by the final review.
- The final disposition made residual risk explicit: five Low/Tier-3 items remain, rather than being hidden by a green test count.

## What could improve: the reusable distinction

### Provenance questions beat coverage questions

Coverage questions found almost nothing: nearly every requirement had a task trace and an asserting test. Provenance questions found most of the 21 defects:

- Who supplies this value?
- Can that supplier lie or future-date it?
- Does this rejection emit its required fact before returning?
- Would this named test fail if the stated behavior broke?

That distinction explains why a suite can have 370 green tests and still miss the ten-minute deadline semantics, caller-controlled creation time, missing rejection facts, host-budget bypasses, and a hard-coded endpoint class. Future reviews must record provenance beside requirement coverage.

### Mutation proof converted green tests into regression protection

Seven tests passed while proving nothing. Examples included an identifier-contiguity assertion that did not prove mapping semantics, an SC-008 test whose confirmed work never happened, and an endpoint-class test whose only case was NativeAdmin, the hard-coded default. The corrective practice is specific: reintroduce the defect, run the named test, and require a failure with a message that identifies the broken behavior. A test is evidence only after this mutation check.

### Controls were complete at one layer and undone above it

Several repairs closed a control in one layer but left the layer above able to undo it. Removing public clock injectors still left a public state-eraser path. Expiry handling charged a budget but returned before checking exhaustion. Reset ordering was fixed at one precheck and then found at two more sites. The recurring review question must be: what is the next caller or wrapper above this control, and can it reintroduce the forbidden state transition?

### Isolation boundaries must be real

`#[doc(hidden)]` and a Cargo feature are visibility or build-selection mechanisms, not isolation boundaries. They do not prevent a production caller from reaching an API in a built configuration. `cfg(test)` is the boundary that actually removes test-only helpers from production compilation. The residual `sign_sealed_for_test` exposure in non-test all-features builds demonstrates why this distinction matters.

### Build freshness affects metric trust

Editing an `include!`d test does not reliably mark the library target dirty. The hazard, tracked as `matinee-9fe`, makes test tallies untrustworthy unless the target directory is independently proven absent or isolated and the library source is touched before the build. The final evidence used a stat-proven separate target directory and touched `crates/matinee-security/src/lib.rs`; that procedure should be mandatory for this layout.

## Actionable improvements

1. **IMP-001 [HIGH] Add provenance prompts to every contract and review matrix.** For each security-sensitive field, record the supplier, trust boundary, and whether the supplier can lie. This would have caught SEC-005 (caller-supplied future `created_ms`), SEC-007 (caller-provided clock, capability, and owner), and SEC-003 (caller-built principals).

2. **IMP-002 [HIGH] Require mutation proof for every security assertion.** Each named test must have a documented mutation target and expected failure message. This would have rejected the seven vacuous tests, including the endpoint-class test that accepted NativeAdmin while the implementation hard-coded Native.

3. **IMP-003 [HIGH] Review controls across the complete call chain, not only the edited function.** For every repair, trace wrappers, prechecks, and state mutation above and below it, then test each exit. This would have found SEC-009 and SEC-010 at all three prechecks and the public state-eraser left after clock-injector removal.

4. **IMP-004 [MEDIUM] Ban claims of isolation based only on `#[doc(hidden)]` or feature flags.** Require `cfg(test)` or an equivalent compilation-removal proof for test helpers, and add an all-features production-compilation check. This targets the `sign_sealed_for_test` residual and prevents test-only APIs from leaking into shipped configurations.

5. **IMP-005 [HIGH] Make build freshness an acceptance precondition for included tests.** The verification recipe should prove `CARGO_TARGET_DIR` is absent or isolated, touch the including library source, then build and record the command. This would have prevented `matinee-9fe` from making green tallies ambiguous.

6. **IMP-006 [MEDIUM] Add a required-fact-before-mutation table to rejection-path tasks.** Every rejection row should name the fact, sink failure behavior, state mutation, and expected ordering. This would have caught SEC-006 (decided creation rejection without a fact), SEC-008 (budget state lost on event failure), and SEC-010 (reset before accepted fact).

7. **IMP-007 [MEDIUM] Keep plan dependency and runtime ownership decisions synchronized with implementation.** A plan change that adds a cryptographic dependency or runtime integration must update the decision record before review. This would have surfaced I1/I8 and avoided the historical SEC-001 dependency divergence.

8. **IMP-008 [LOW] Use canonical task identifiers in review handoffs and trace links.** Reject shorthand IDs that do not resolve in `tasks.md`, while preserving historical aliases in notes. This would have prevented I2 and I3 and reduced ambiguity during convergence.
